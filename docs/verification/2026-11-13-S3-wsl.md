# Verification: S3, WSL2 compute node on the office PC, 2026-11-13

**Question (PLAN §6.1, spike S3):** can the office PC run μ's Linux toolchain in WSL2 as an always-on compute node:
Ubuntu imported, a systemd service running, starting after a reboot **with nobody signed in**, and the memory setting
applied?
**Answer:** yes. After a reboot the distro and its systemd service ran for **2 h 01 min with nobody signed in** to
Windows. No Windows service wrapper is needed, so the fallback (a wrapper or the Hyper-V adapter) is not used.

## Setup

All of it is reversible, and none of it needs a second Windows account.

**Distro.** `wsl --install Ubuntu-24.04 --name mu-compute --location C:\Mu\wsl\mu-compute --no-launch`. The
first launch runs Ubuntu's setup, which creates an admin user (`ak`, with sudo). μ runs as a separate user `mu`
**without sudo**; admin work goes through `wsl -d mu-compute -u root`.

`/etc/wsl.conf`:
```
[boot]
systemd=true
[user]
default=mu
[interop]
appendWindowsPath=false
```

`C:\Users\ak\.wslconfig` (applies to every distro of that Windows user):
```
[general]
instanceIdleTimeout=-1
[wsl2]
memory=23GB
processors=20
swap=8GB
guiApplications=false
```
Checked inside Linux: 20 CPUs, 22 GiB memory, 8 GiB swap, systemd as PID 1.
`instanceIdleTimeout=-1` (WSL ≥ 2.5.4) is what keeps the instance alive. A running systemd service alone does not.

**Repo access.** `mu` has its own SSH key, registered on `martand-systems/mu` as a **read-only deploy key**
(the org setting allowing deploy keys was turned on for this). `known_hosts` pins GitHub's ed25519 key, checked
against `api.github.com/meta`.

**Start at boot.** A scheduled task `\mu\mu-compute` runs
`"%ProgramFiles%\WSL\wsl.exe" -d mu-compute --exec /bin/true`:
- trigger: at startup, 30 s delay, then repeated every 5 minutes (the repeat is the watchdog: a WSL update stops
  the WSL service and the instance with it);
- principal: user `ak`, **S4U** ("run whether the user is signed in or not", no stored password), highest privileges;
- 5-minute limit, a new run is skipped while one is still running.

The SYSTEM account can't be used: WSL refuses it (`WSL_E_LOCAL_SYSTEM_NOT_SUPPORTED`). WSL keys sessions by user SID,
and a session started from session 0 lasts until the WSL service stops.

**Power.** Sleep and hibernate on AC off. Fast Startup off (`HiberbootEnabled=0`). Automatic sign-in after a
restart off (`DisableAutomaticRestartSignOn=1`). That last setting also matters for the test, see below.

**Stand-in for the agent.** Until the relay agent exists (S4), `mu-heartbeat.service` (User=mu, `Restart=always`)
appends the UTC time to `/home/mu/heartbeat.log` every 60 s. `loginctl enable-linger mu` keeps `mu`'s user
services (the auto-updater's timer) running without a login.

## Results

| Test | Result |
|---|---|
| Close every window, sign-in kept | **pass**: distro `Running`, heartbeat continuous |
| Reboot 1 | inconclusive: Windows signed `ak` in by itself 13 s after boot (Automatic Restart Sign-On), so "nobody signed in" was not tested. ARSO turned off |
| Sign out of Windows | **pass**: heartbeat continuous 09:15–09:19Z across the sign-out and re-sign-in |
| **Reboot 2, left at the sign-in screen** | **pass**, see below |

Reboot 2:
- boot 09:20:33Z, first sign-in (explorer) 11:21:21Z, so **2 h 01 min with nobody signed in**;
- first heartbeat 09:21:15Z, **42 s after boot** (30 s task delay plus distro start), then 124 more to the end of
  the test with **no gap over 61 s**: the service started once and never restarted;
- `wsl -l -v`: `mu-compute Running`; the task's last run (the 5-minute repeat) returned 0.

**Finding: a Windows restart does not shut Linux down cleanly.** The last line written before the restart
(09:20:03Z, 30 s before boot) came back as 21 zero bytes, exactly the length of one heartbeat line. The file's size
had been updated but its data never reached the disk. Windows stops the WSL VM without a Linux shutdown, so writes
in the last seconds before a restart can be lost. Consequences:
- the relay agent (S4) writes its state and job records atomically: write a temp file, `fsync`, rename;
- jobs interrupted by a restart are re-run, not trusted;
- Windows should stop the distro before a restart (`wsl --terminate mu-compute` from a shutdown script). To be added
  with the host setup scripts and re-tested with a reboot.

## Problems found, and their fixes (v2026.11.6)

- **A dropped download restarted from zero.** ParaView's 912 MB tarball failed with `curl: (56) Recv failure`, and
  the fallback deleted the partial file. The new downloader (`install/download.sh`) resumes instead of restarting,
  cuts stalled connections, and fetches large files over 8 connections in parallel. 31 test cases pass, including
  this failure.
- **Preflight reported 934 GB free.** That is the virtual disk's maximum size, not the free space on C:. On WSL the
  installer and the auto-updater now check the Windows drive that holds the distro.
- **PrusaSlicer was downloaded from Flathub on every reinstall.** Pinned Flathub commits are now cached once per
  machine, so a reinstall works offline.

Not tested yet: surviving a WSL update (the 5-minute repeat should restart the instance) and a Windows Update
restart. Both are covered by the same start-at-boot task, and are checked when they first happen.

## Decision

S3 passes. The office PC is the always-on compute node, using plain WSL2 with systemd, a startup scheduled task
under S4U, `instanceIdleTimeout=-1` and ARSO off. PLAN's fallback (a Windows service wrapper) is not needed.
The heartbeat service is replaced by the relay agent in S4.
