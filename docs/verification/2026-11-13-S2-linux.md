# Verification: S2, linux-64 provisioning (Ubuntu 24.04, headless), 2026-11-13

**Question (PLAN §16):** does every tool have a working headless Linux route? If one doesn't, that tool is marked
`local`-only. FEA and CFD must pass.
**Answer:** yes, every tool, with the same versions as macOS. Where the tools are deterministic, the results equal the
macOS reference.

**Test bed:** GitHub-hosted `ubuntu-24.04` runners (x86_64, 2 vCPU, 8 GB), private repo. Every test runs in a fresh
container from two images:
- plain `ubuntu:24.04`;
- the **official Ubuntu 24.04 WSL image** (`ubuntu-noble-wsl-amd64-wsl.rootfs.tar.gz`), which is what the office PC's
  WSL2 distro starts from.

Workflows: `.github/workflows/s2-probe.yml` (per-tool probes) and `linux-install.yml` (the full user install). Both run on
demand. Scripts are in `tools/s2/`.

**Found and fixed during the probes:**
- Bare `ubuntu:24.04` lacks libGL (needed by the OCP wheels) and the X client libraries that ParaView's OSMesa path loads.
  The WSL image has them. This became the declared list `toolchain/linux-64/apt.txt`.
- flatpak needs a session D-Bus (`dbus-run-session`) and the system D-Bus. WSL2 with systemd has it; containers must start it.
- CMake can't unpack OpenVSP's bundled zips in the C locale. The Linux installer defaults to `C.UTF-8`.

- The installer's apt check: Ubuntu 24.04 renamed `libxt6` to `libxt6t64`. Under the old name apt installs it but
  dpkg reports it missing, so every install would have asked for sudo again.
- OpenVSP's CHARM declares `opencv-python` and `PyAutoGUI`. On Linux μ uses `opencv-python-headless` (the same `cv2`), and
  CHARM never imports PyAutoGUI. Metadata-only stubs in `toolchain/linux-64/pip-stubs` keep the dependency check strict.
- A tutorial copied out of the read-only store is read-only too. The CFD benchmark (and the Claude instructions) now
  make the copy writable.

## Decision

S2 passes. Every tool has a working headless linux-64 route, including FEA and CFD. Nothing is `local`-only. The design
is unchanged (ADR-001 holds). Per-tool notes:
- **PrusaSlicer** depends on Flathub keeping old commits. Mirror the pinned commit (or build from the Flathub manifest)
  before relying on it long-term.
- **OpenVSP's API** is built on the device. A prebuilt, hash-pinned artifact served by the relay is an optional later
  speed-up.
- **Containers** (a later Linux server) need `--privileged` for flatpak and a system D-Bus. WSL2 with systemd needs neither.

## Follow-up (release 2026.11.5): PrusaSlicer download cache, WSL disk check

**Before:** each new PrusaSlicer layer ran `flatpak install` (Flathub's latest build plus every related ref, unpinned)
and then `flatpak update --commit=<pin>` for the app and the runtime. Nothing was cached: a fresh `MU_HOME`, a
`--rebuild` or a new layer key downloaded ~1–2 GB from Flathub again, and the layer (2.8 GB) also held translations,
GL drivers and codecs at whatever versions Flathub had that day.

**Now (`install/flatpak.sh`):**
- **Download cache:** `$MU_CACHE/flatpak`, a flatpak installation used only for downloading. Its OSTree repository holds
  each pinned commit (app and runtime), downloaded **once per machine, straight at the pin** with
  `flatpak update --commit=<pin> --no-deploy`. That command needs the ref installed, so the ref is first installed from
  an empty placeholder commit made locally (its metadata copied from Flathub's summary; nothing is downloaded for it).
  flatpak checks Flathub's signatures with Flathub's key, which is now pinned in the recipe
  (`toolchain/linux-64/flathub.gpg`, fingerprint 6E5C 05D9 79C7 6DAF 93C0 8135 4184 DD4D 907A 7CAE). A ref
  `mu/<ref>/<commit>`, written once the commit is complete, marks it cached. A `flock` serialises downloads into one
  cache. An interrupted download resumes (fetched objects stay; the commit stays marked partial).
- **Why not the `ostree` CLI:** Flathub answers HTTP 403 to the plain `libostree` client for objects, so every
  download has to go through flatpak.
- **Layer:** built with **no network**. `ostree pull-local --untrusted` imports the two commits into the layer's own
  repository and checksums every object again. `flatpak install --no-pull --no-related` deploys them, and the deployed
  commits are compared with the pins. Only the app and its runtime are installed. The related refs (translations, GL
  drivers, codecs) are not pinned and the headless CLI doesn't need them. Layer: **1.3 GB (was 2.8 GB)**.
- **Disk:** the layer is a **copy**: on one filesystem `pull-local` hard-links the cache's objects, so the installer
  then copies the layer's objects (`cp -a --reflink=auto`: shared extents on btrfs/XFS, a plain copy on ext4). With hard
  links (the first version of this branch) a write into any one file changed the cache and every other layer at once,
  repairing the cache left the layers damaged, and the layer's files could not be sealed, because a bare-user-only
  object's mode is part of its checksum and the cache had the same inodes. As a copy, the layer is sealed like every
  other layer (`chmod -R a-w`), the cache can be repaired or deleted without touching any layer, and the reverse. Cost:
  a layer takes its full 1.3 GB next to the cache (still less than the 2.8 GB layer before). If an object in the cache
  fails its checksum on import, the installer repairs the cache (`ostree fsck --delete`, then downloads again) and
  retries.
- **Pruning:** each version lists its pinned commits in `toolchains/<v>/CACHE_REFS`. `MU_CACHE` is shared by every
  `MU_HOME` of the user (a test install, a second tree), so each installer also records its `MU_HOME` in
  `~/.cache/mu/flatpak/homes/`. `mu gc` and `mu remove` (in any `MU_HOME`) keep every commit an installed version of any
  recorded `MU_HOME` pins, delete the other cached commits, then the objects that nothing references
  (`ostree prune --refs-only`, on every `gc --yes`, so interrupted downloads are reclaimed too; skipped while a pinned
  commit is itself half downloaded). A record whose `MU_HOME` is gone is dropped. A remote ref that a killed download
  left on a real commit is put back on the placeholder first. **Locking:** downloads hold `flatpak.lock` exclusively,
  imports into a layer hold it shared, and gc prunes only if it gets it exclusively at once. If a commit a layer needs
  was pruned anyway (gc in another `MU_HOME` before this install recorded its pins), the import downloads it again.
  The other downloads in `MU_CACHE` are still not pruned, as before; all of it can be deleted safely.
- **Layer key:** the PrusaSlicer layer is now keyed by `FLATPAK_FORMAT`, the app commit and the runtime `ref@commit`.
  The runtime was missing from the key before. `LAYER_FORMAT` is unchanged: it only affects the env and CAM layers,
  which are built the same way as before. So the upgrade rebuilds only the PrusaSlicer layer: one ~520 MB download,
  then no network.

**Probe (`s2-probe`, prusaslicer, both images):** the first download was killed after 20 s and resumed. A second install
fetching the same commit waited on the lock and did not download it again. Cold download: **522 MB** over the network
(1,292 MB in the cache). Warm fetch: **0 bytes**. Two layers built under `unshare -n` (no network at all), 8 s each.
`ostree fsck` of the cache was clean after both layers were built and sealed. One object was damaged on purpose: the next
layer build repaired it and passed. Slicing from the offline-built layer gave **11.86 g, 30 layers**.

In CI, `~/.cache/mu` is a separate bind mount, so install #2 copied the objects instead of hard-linking them (1.4 GB
of new disk). On a real machine the two share a disk.

**WSL disk check (`install/disk.sh`, the same block in `bin/mu`):** on WSL2, `df /` reports free space inside the
distro's `ext4.vhdx`, a sparse disk whose limit (1 TB by default) can be far more than what is free on the Windows drive
under it. The preflight and auto-update's `min_free_gb` now count the smaller of the two. The drive comes from the
distro's `BasePath` (HKCU `...\Lxss`, matched by `$WSL_DISTRO_NAME`), read with `reg.exe` by full path, and is mapped
to its drvfs mount from `/proc/mounts`. Example: `Preflight · 130 GB free on C: (WSL disk)`. Fallbacks:
- the drive is enforced only when it is known for certain: this distro found by name, or every registered distro on
  one drive;
- otherwise only the VHD figure is enforced, and the guessed drive's free space is shown and warned about when low
  (`! 6 GB free on C: if the WSL disk is there (no answer from Windows (reg.exe), so C: is assumed); this install
  needs about 10 GB`), never enforced: a guess must not stop an install or every auto-update. Guesses: interop off, no
  answer within 15 s, or a `BasePath` with no drive letter: C:; no distro name (ssh, the systemd timer, `env -i`) and
  distros on several drives: the least free of them;
- no mount for the drive, or `df` failing on it (a drive gone away): the VHD only, with a note.

`tools/test-wsl-disk/run.sh` covers these cases (27 stubbed cases, including CRLF and UTF-16LE output, `\\?\` paths, a
mount path with a space, a caller's IFS and `df` failing; each case runs under `set -Eeuo pipefail` with an ERR trap, as
in the installer) under bash 3.2 and 5. `tools/test-autoupdate` has a WSL case. Still to do
on the office PC: check what `reg.exe` really outputs through a pipe there. The parser handles ANSI/OEM and UTF-16.
