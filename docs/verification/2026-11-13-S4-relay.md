# Verification: S4, chisel through Dokploy's Traefik, 2026-11-13

**Question (PLAN §7, spike S4):** does the relay design work with the Traefik that Dokploy runs on the server: a
reverse tunnel from one client, a forward from another, a long idle period, and reconnects, all over
`wss://relay.martand.systems` on 443?
**Answer:** yes, **in a replica of the server built in CI**. With Dokploy's Traefik configuration and each Traefik
version Dokploy has shipped since v0.29, the tunnel carried 100 MB each way unchanged, stayed up through **20 minutes
with no traffic at all**, and came back by itself after a redeploy, a Traefik restart, a restart of the compute end
and a silent loss of its network. The fallbacks (frp over WebSocket, a high port) are not needed.
The real server was not touched, so this is not yet a test of that server. What is still open is listed below.

## Test bed

Nothing ran on the server, in Dokploy or in DNS. The replica runs on a GitHub-hosted `ubuntu-24.04` runner
(Docker 28.0.4), built by `tools/s4/run.sh`:

| Part | How it matches the server |
|---|---|
| Traefik | Started with the `docker run` line of Dokploy's `createTraefikInstance()` (container `dokploy-traefik`, ports 80, 443, 443/udp), with Dokploy's static config for a deploy server (`getDefaultServerTraefikConfig()`: providers swarm, docker and file, entrypoints `web` and `websecure` with HTTP/3, resolver `letsencrypt`, **no timeouts set**) and its `redirect-to-https` middleware. Versions **3.6.7, 3.6.25 and 3.7.16**: what Dokploy pinned up to v0.29.14, in v0.30.x and from v0.31.0. The server was set up 2026-08-20, so 3.6.25 is the most likely one; it was not read |
| Network | A one-node swarm and an attachable overlay network `dokploy-network`, as Dokploy's server set-up makes them |
| Relay | `relay/compose.yaml` and `relay/Dockerfile` exactly as in git, started with Dokploy's command line (`docker compose -p <appName> --env-file relay/.env -f relay/compose.yaml up -d --build --remove-orphans`) and an env file in the format Dokploy writes |
| Labels | The labels and networks Dokploy's `addDomainToCompose()` adds for the planned Domains entry (host `relay.martand.systems`, port 8080, HTTPS, Let's Encrypt), as a Compose override. Dokploy rewrites the file instead; the result is the same service definition |
| Clients | Containers on their own networks, outside `dokploy-network`. They reach the relay only through the published port 443. `relay.martand.systems` resolves to the runner inside these containers only |
| Credentials | Made in the run by `relay/gen-credentials.sh`, as the real ones will be |

Three things differ from the server on purpose:

- **Certificate.** A throw-away CA and a certificate loaded through Traefik's file provider (the way Dokploy loads
  custom certificates). The ACME resolver is defined but points at a dead address, so nothing can reach Let's Encrypt.
- **`DOCKER_CONFIG`.** Dokploy adds `DOCKER_CONFIG=/root/.docker` to the env file; the replica writes the
  runner's own path there (see findings).
- **chisel 1.12.0 runs at both ends** from the image built from `relay/`, in Linux containers. Not on WSL2, not on
  macOS.

Traefik's `readTimeout` is 60 s and its `idleTimeout` 180 s. Neither applies to a tunnel once it is upgraded: the
tunnel with keepalive off was one connection for 21 min 49 s, 1217 s of it without a byte, and was closed only by the
Traefik restart later in the run.

The throughput (52–100 MB/s) is one machine talking to itself and says only that the relay's 0.5 CPU limit is not
in the way of the < 10 MB a job moves (PLAN §6.4).

**What the chisel client does on the wire:** it sends no ALPN extension and upgrades with a plain HTTP/1.1
`GET` + `Upgrade: websocket`, subprotocol `chisel-v3`. So Traefik offering `h2` and advertising HTTP/3 on
`websecure` does not matter. (The same probe sees curl offer `h2`.)

**Access rules** (`relay/entrypoint.sh` turns `RELAY_CLIENTS` into one anchored rule per client), tested against the
running relay:

| Attempt | Result |
|---|---|
| Wrong password; no credentials | refused (`unable to authenticate`) |
| Relay with a key other than the pinned fingerprint | the client refuses (`Invalid fingerprint`) |
| Workstation credentials, forward to `dokploy-traefik:8080` (Traefik's API, which the relay container itself can reach) | `access to 'dokploy-traefik:8080' denied` |
| Workstation credentials, a reverse tunnel | denied |
| Compute credentials: listen on `0.0.0.0:7001`, on port 7002, or open a forward | denied, all three |
| A second client with the compute credentials while the first is connected | `Server cannot listen on R:127.0.0.1:7001`; the first is not disturbed |
| A neighbouring container on `dokploy-network` connecting to the compute port on the relay's address | connection refused (the port is on the relay's loopback only) |
| Passwords or key in the relay's log; `RELAY_` variables in chisel's environment | none; none |
| Limits from `compose.yaml` on the running container | read-only root, uid 65532, all capabilities dropped, 256 MiB, 0.5 CPU, 256 pids, no published port, no mount |

`tools/s4/test-config.sh` (53 checks, no Docker) tests the credential tool and the entrypoint: 25 kinds of
malformed input are refused before chisel starts, and the generated rules match exactly the client's own tunnel. It
was run with three faults put in (unanchored rule, 2-character password accepted, locale fix removed) and failed
each time.

## Found, and what was done

- **A redeploy cost 33 s; now 13 s.** In the first full run (43443179540) the tunnel took 33.2–33.3 s to return
  after the relay container was recreated, on all three Traefik versions. The new container was listening within
  the same second. But Traefik still routes to the removed container for a moment (it applies Docker events after
  a 2 s throttle), the clients' first retry (1 s after the drop) lands there, and it waits for Traefik's 30 s dial
  timeout: the client logs show nothing for 31 s, then `bad handshake`. The clients now run with
  `CHISEL_WS_TIMEOUT=10s` (chisel's handshake timeout, default 45 s): the first retry gives up after 10 s, the
  second connects, 13.2–13.4 s in all. One test client keeps the default and still takes 33.3–33.5 s in every run.
  Traefik's own timeout could shorten this further, but the relay does not change Traefik's configuration.
- **Without `start_interval` every deploy would answer `404` for 30 s.** Traefik does not route to a container whose
  health is still "starting", and Docker runs the first probe only after `interval`. `compose.yaml` sets
  `start_period: 15s` and `start_interval: 1s`: routable 1.9–2.7 s after start. Needs Docker Engine 25 or later.
- **Relay credentials must not be a way into `dokploy-network`.** A chisel server lets an authenticated client
  forward to anything the container can reach, and Traefik's API (`api.insecure`, port 8080) is reachable from every
  container on that network. The entrypoint therefore gives each client one rule: a compute node may listen on its
  own loopback port of the relay, a workstation may connect to the listed loopback ports. Tested above.
- **`gen-credentials.sh` accepted the name `Mac` on macOS.** In a UTF-8 locale bash matches upper-case letters
  against `[a-z]`. The relay's entrypoint would then have refused to start after the deploy. Both scripts now set
  `LC_ALL=C`. Found by `test-config.sh`.
- **Dokploy's env file reaches `docker compose` itself, not only the `${…}` in the compose file.** The first CI run
  (43442967921) failed to build because the replica copied Dokploy's `DOCKER_CONFIG=/root/.docker` line and the
  runner is not root. On the server Dokploy deploys as root, so the line is right there. Consequence: no
  `COMPOSE_…` or `DOCKER_…` variable belongs in the relay's Environment tab.
- **A link that dies silently is noticed only by the keepalive**, after up to 50 s (a 25 s interval plus a 25 s
  reply timeout). In the long run the relay and the compute end both closed the dead session 50.0 s after it had
  opened, and the cut came a second or two after that opening. Until then a workstation request hangs or fails.
  After that the relay frees the
  port and the compute end reconnects (9.6–9.9 s after its network returned). `mu` should treat about a minute of
  failures after a network change as normal before falling back to `local`.
- **A Traefik restart drops every tunnel on the server** after its 10 s grace period; clients were back 11.5–13.1 s
  after the restart began. This is what the *Reload* and *Update* buttons for Traefik in Dokploy do.
- **Compute credentials can be used by someone else while the PC is offline** (not while it is connected, see the
  table). The relay cannot tell. This is what the agent's own pinned TLS certificate inside the tunnel is for
  (PLAN §7.2); the tunnel alone is not the trust boundary.
- A test bug, for the record: run 43443179540 failed one row in each job because the driver compared `OK\n 200`
  with `OK 200`. Everything else in that run passed.

## Not proven until the real server

1. **The server's actual Traefik**: its version and whether `/etc/dokploy/traefik/traefik.yml` was ever edited
   (timeouts, middlewares). The Dokploy CLI's detail calls return HTTP 400, so neither was read. Dokploy shows the
   image under Remote Servers → Setup Server → Validate.
2. **Let's Encrypt** for `relay.martand.systems`: HTTP-01 through port 80, with the resolver as that server has it
   (the default e-mail is `test@localhost.com`). CI used its own CA. An existing HTTPS site on that server with a
   valid certificate would show the resolver works.
3. **Dokploy's own deploy**: the clone through the GitHub app, its rewrite of `compose.yaml`, the env file from the
   Environment tab, the build on the server (it downloads chisel from GitHub and pulls Alpine), and Docker Engine
   25 or later there for `start_interval`.
4. **A real network path**: NAT, carrier and hotel idle timers, the office's outbound firewall, WSL2's NAT, real
   latency and bandwidth. The 25 s keepalive is there for these; only a hop that cuts after 45 s was tested.
5. **The real clients**: chisel on the office PC's WSL2 distro as `mu` and on the Mac, the Mac sleeping and
   changing networks, the PC rebooting with the client under systemd.
6. **Idle for longer than 20 minutes**, and days of uptime.
7. **Life next to the other 12–15 containers**: their deploys (one neighbour was tested), the server's memory, a
   Traefik update or a reboot of the server.
8. **The inner layer** (agent TLS and token, PLAN §7.2) does not exist yet. The test payload was plain HTTP inside
   the tunnel.

## First check on the real server

The Dokploy steps are in `relay/README.md` §2; the owner does them in the UI. The values for the Environment tab
come from `relay/gen-credentials.sh`, run by the owner on the Mac (state in `~/.config/mu/relay.env`, mode 600):

```sh
relay/gen-credentials.sh init
relay/gen-credentials.sh add-client compute office-pc 7001
relay/gen-credentials.sh add-client workstation avi-mac 7001
relay/gen-credentials.sh env        # the two lines to paste: RELAY_KEY=… and RELAY_CLIENTS=…
```

After the deploy, `curl -sS https://relay.martand.systems/health` prints `OK` with a valid certificate. Then, with
the fingerprint and passwords from `gen-credentials.sh client office-pc` and `client avi-mac`:

```sh
# office PC, in the mu-compute distro, as mu (no sudo needed): chisel, a stand-in for the agent, the reverse tunnel
mkdir -p ~/s4-check/www && cd ~/s4-check
curl -fsSL -o chisel.gz https://github.com/jpillora/chisel/releases/download/v1.12.0/chisel_1.12.0_linux_amd64.gz
echo "f3f180f1d93aa72cce4e6386f98cc06569a0146fbd65eb4423cf83e6434bcfe6  chisel.gz" | sha256sum -c -
gunzip -c chisel.gz > chisel && chmod 755 chisel && ./chisel --version        # 1.12.0
echo "hello from office-pc" > www/hello.txt
python3 -m http.server 9000 --bind 127.0.0.1 --directory www &
AUTH='office-pc:<RELAY_PASSWORD>' CHISEL_WS_TIMEOUT=10s ./chisel client --fingerprint '<RELAY_FINGERPRINT>' \
  --keepalive 25s --max-retry-interval 15s https://relay.martand.systems R:127.0.0.1:7001:127.0.0.1:9000

# Mac, away from the office LAN: chisel, the forward, then a request through it from a second terminal
mkdir -p ~/s4-check && cd ~/s4-check
curl -fsSL -o chisel.gz https://github.com/jpillora/chisel/releases/download/v1.12.0/chisel_1.12.0_darwin_arm64.gz
echo "707a4b932eea214765146504a0df246cefc415b4297af65a80dd67cf69ba85a9  chisel.gz" | shasum -a 256 -c -
gunzip -c chisel.gz > chisel && chmod 755 chisel && ./chisel --version        # 1.12.0
AUTH='avi-mac:<RELAY_PASSWORD>' CHISEL_WS_TIMEOUT=10s ./chisel client --fingerprint '<RELAY_FINGERPRINT>' \
  --keepalive 25s --max-retry-interval 15s https://relay.martand.systems 127.0.0.1:7001:127.0.0.1:7001
curl -s http://127.0.0.1:7001/hello.txt        # hello from office-pc
```

The stand-in serves one file from an empty folder: until the agent exists, whatever the PC exposes on that port is
readable by anyone holding the workstation's credentials.

Leave both clients running for an hour and repeat the `curl`; then press Deploy again in Dokploy and repeat it
after 15 s. Both client logs should then show one `Disconnected` and one new `Connected`. That covers items 1–5
above for the first time.

## Decision

S4 passes in the replica: chisel behind Dokploy's Traefik on 443 is the relay (PLAN §7.3 Stage A). No Traefik
setting has to change and no host port is needed, so the fallbacks are dropped. Fixed by this spike for P6:

- clients run with `--keepalive 25s`, `--max-retry-interval 15s`, `CHISEL_WS_TIMEOUT=10s` and a pinned fingerprint;
- the relay's health check keeps `start_interval`;
- every client has its own credentials and one access rule, made by `gen-credentials.sh` (later `mu relay add-client`);
- the Dokploy service gets Watch Paths `relay/**`, so that only relay changes redeploy it.

The spike is closed when the first check on the real server has been done and its numbers are added here.
