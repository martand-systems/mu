# Verification: S4, chisel through Dokploy's Traefik, 2026-11-13

**Question (PLAN §7, spike S4):** does the relay design work with the Traefik that Dokploy runs on the server: a
reverse tunnel from one client, a forward from another, a long idle period, and reconnects, all over
`wss://relay.martand.systems` on 443?
**Answer:** yes, **in a replica of the server built in CI**. With Dokploy's Traefik configuration and each Traefik
version Dokploy has shipped since v0.29, the tunnel carried 100 MB each way unchanged, stayed up through **20 minutes
with no traffic at all** on every version, and came back by itself after a redeploy, a Traefik restart, a restart of
the compute end and a silent loss of its network. In the replica the fallbacks (frp over WebSocket, a high port) are
not needed.
The real server was not touched, so this is not yet a test of that server. What is still open is listed below.

## Test bed

Nothing ran on the server, in Dokploy or in DNS. The replica runs on a GitHub-hosted `ubuntu-24.04` runner
(Docker 28.0.4), built by `tools/s4/run.sh`:

| Part | How it matches the server |
|---|---|
| Traefik | Started with the `docker run` line of Dokploy's `createTraefikInstance()` (container `dokploy-traefik`, ports 80, 443, 443/udp), with Dokploy's static config for a deploy server (`getDefaultServerTraefikConfig()`: providers swarm, docker and file, entrypoints `web` and `websecure` with HTTP/3, resolver `letsencrypt`, **no timeouts set**) and its `redirect-to-https` middleware. Versions **3.6.7, 3.6.25 and 3.7.16**: what Dokploy pinned up to v0.29.14, in v0.30.x and from v0.31.0. The server was set up 2026-08-20, so 3.6.25 is the most likely one; it was not read |
| Network | A one-node swarm and an attachable overlay network `dokploy-network`, as Dokploy's server set-up makes them |
| Relay | `relay/compose.yaml` and `relay/Dockerfile` exactly as in git, started with Dokploy's command line (`docker compose -p <appName> --env-file relay/.env -f relay/compose.yaml up -d --build --remove-orphans`) and an env file in the format Dokploy writes |
| Labels | The labels and networks Dokploy's `addDomainToCompose()` adds for the planned Domains entry (host `relay.martand.systems`, port 8080, HTTPS, Let's Encrypt, Middlewares `mu-relay-inflight@docker`), as a Compose override. Dokploy rewrites the file instead; the result is the same service definition |
| Clients | Containers on their own networks, outside `dokploy-network`. They reach the relay only through the published port 443. `relay.martand.systems` resolves to the runner inside these containers only |
| Credentials | Made in the run by `relay/gen-credentials.sh`, as the real ones will be |

Three things differ from the server on purpose:

- **Certificate.** A throw-away CA and a certificate loaded through Traefik's file provider (the way Dokploy loads
  custom certificates). The ACME resolver is defined but points at a dead address, so nothing can reach Let's Encrypt.
- **`DOCKER_CONFIG`.** Dokploy adds `DOCKER_CONFIG=/root/.docker` to the env file; the replica writes the
  runner's own path there (see findings).
- **chisel 1.12.0 runs at both ends** from the image built from `relay/`, in Linux containers. Not on WSL2, not on
  macOS.

## Found, and what was done

- **A redeploy cost 33 s; now 13 s.** In the first full run (43443179540) the tunnel took 33.2–33.3 s to return
  after the relay container was recreated, on all three Traefik versions. The new container was listening within
  the same second. But Traefik still routes to the removed container for a moment (it applies Docker events after
  a 2 s throttle), the clients' first retry (1 s after the drop) lands there, and it waits for Traefik's 30 s dial
  timeout: the client logs show nothing for 31 s, then `bad handshake`. The clients now run with
  `CHISEL_WS_TIMEOUT=10s` (chisel's handshake timeout, default 45 s): the first retry gives up after 10 s, the
  second connects, 13.3–13.5 s in all. One test client keeps the default and still takes 33.2–33.5 s in every run.
  Traefik's own timeout could shorten this further, but the relay does not change Traefik's configuration.
- **Without a start period every deploy would answer `404` for 30 s.** Traefik does not route to a container whose
  health is still "starting", and with neither `start_period` nor `start_interval` Docker runs the first probe only
  after `interval` (30 s). `compose.yaml` sets `start_period: 15s` and `start_interval: 1s`: routable 2.3–3.3 s
  after start. With `start_period` alone Docker would probe every 5 s. `start_interval` needs Docker Engine 25 or
  later.
- **Relay credentials must not be a way into `dokploy-network`.** A chisel server lets an authenticated client
  forward to anything the container can reach, and Traefik's API (`api.insecure`, port 8080) is reachable from every
  container on that network. The entrypoint therefore gives each client one rule: a compute node may listen on its
  own loopback port of the relay, a workstation may connect to the listed loopback ports. Tested above.
- **A port written `07001` was a second name for port 7001.** Both scripts accepted it, and the check for a compute
  port used twice compared the text. chisel listens on 7001 for it, so two compute nodes could be given the same
  port: whichever connected first got it, and a workstation allowed one of them reached the other. Both scripts now
  refuse a leading zero. Found by the review.
- **A chisel server keeps a connection that never logs in open for ever.** It has no time limit before the log-in,
  and Dokploy's Traefik sets none either. In the review, 3000 such connections to a local chisel 1.12.0 were all
  still open after 90 s and took its memory from 7 MB to about 74 MB. Enough of them reach the relay's 256 MiB;
  Docker then restarts it and every tunnel reconnects. `compose.yaml` now defines a Traefik middleware that allows
  32 connections at a time per client address (an IPv6 /64 counts as one address), and the Domains entry names
  it. Traefik's default would count per host name, where 32 idle connections lock everybody out, so the labels
  say "per address". **What is left:** a container on `dokploy-network` reaches the relay's port 8080 directly,
  with no limit; and somebody with some hundreds of addresses can still fill the memory. Neither exposes
  anything; both can make the relay unavailable.
- **`gen-credentials.sh` accepted the name `Mac` on macOS.** In a UTF-8 locale bash matches upper-case letters
  against `[a-z]`. The relay's entrypoint would then have refused to start after the deploy. Both scripts now set
  `LC_ALL=C`. Found by `test-config.sh`.
- **Dokploy's env file reaches `docker compose` itself, not only the `${…}` in the compose file.** The first CI run
  (43442967921) failed to build because the replica copied Dokploy's `DOCKER_CONFIG=/root/.docker` line and the
  runner is not root. On the server Dokploy deploys as root, so the line is right there. Consequence: no
  `COMPOSE_…` or `DOCKER_…` variable belongs in the relay's Environment tab.
- **A link that dies silently is noticed only by the keepalive**, after up to 50 s (a 25 s interval plus a 25 s
  reply timeout). The relay closed the dead session 50.00 s after it had opened, in all 6 cases (the cut
  network and the frozen container, on each version); the cut came a second or two after that opening. Until then
  a workstation request hangs or fails. After that the relay frees the port and the compute end reconnects
  (9.6–10.0 s after its network returned). `mu` should treat about a minute of failures after a network change as
  normal before falling back to `local`.
- **A compute end that dies without a close and is back within those 50 s is refused by its own old session.** The
  relay still holds the dead session and its port, and answers `Server cannot listen on R:127.0.0.1:7001`. The
  client keeps trying: in the test (the first container frozen, a second one with the same credentials started
  at once) it was refused 7 times and connected after 60.4–60.7 s. The worst case is about 65 s: 50 s for the
  relay to notice, then the client's next try, up to 15 s later. A clean restart, where chisel closes the session
  first, took 1.8–2.2 s. A PC that loses power rarely boots within 50 s; a WSL VM that is killed and started
  again does. When the frozen container was thawed and the second one removed, it had its port back after
  1.1–1.2 s. The relay's ping timeout could be shortened (`CHISEL_PING_TIMEOUT`); it was left at chisel's default
  because a minute is already what `mu` has to allow after a network change, and the idle results above were
  measured with the default.
- **A Traefik restart drops every tunnel on the server** after its 10 s grace period; clients were back 11.6–11.8 s
  after the restart began. This is what the *Reload* and *Update* buttons for Traefik in Dokploy do.
- **Compute credentials can be used by someone else while the PC is offline** (not while it is connected, see the
  table). The relay cannot tell. This is what the agent's own pinned TLS certificate inside the tunnel is for
  (PLAN §7.2); the tunnel alone is not the trust boundary.
- **In Stage A the server can read the job data.** The relay joins two plain TCP streams. The relay container, and
  anyone with root or Docker access on the server, sees everything that passes, and has the key and every client
  password (`relay/.env` on the server's disk, `docker inspect`). Traefik and the network in between see only
  chisel's encrypted stream. The pinned fingerprint tells a client that it talks to this relay; it does not hide
  anything from the relay. PLAN §7.2 and §11 describe end-to-end encryption between laptop and agent: that is true
  once the agent's TLS runs inside the tunnel, and not before. Until then nothing may be exposed on a compute port
  that the server's administrators may not read.
- A test bug, for the record: run 43443179540 failed one row in each job because the driver compared `OK\n 200`
  with `OK 200`. Everything else in that run passed.

## Review

The first build (run 43444991890, commit `f95cc9a`) was finished by one agent with no second reader. Two independent
reviews followed: one of security, one of whether the tests prove what this record says. They found 3 and 13
problems. All 16 were real and all were dealt with before this run, in the code, the tests or this record. The main
ones:
- a port written `07001` gave two compute nodes the same port
- nothing limited connections that never log in, so the relay could be filled up from outside
- the plan reads as if the relay could not see job data, and the record did not say plainly that in Stage A the
  server can
- a compute end back within 50 s of an unclean death is locked out by its own stale session, and no row tested it
- the access rows used only chisel's own client, which never asks for a tunnel it did not declare
- the "test of the test" broke one thing, at the first relay row; the normal way for a row to fail never ran in CI
- the summary claimed 20 minutes of silence for every Traefik version when two had idled for 4 minutes
- the first check on the real server could pass without the relay having restarted
- the redeploy row did not check that the container was replaced
- the slow health check control and the finding built on it were mislabelled ("30 s" is right with neither line,
  "5 s" with `start_period` alone)
- the locale check could not fail on Linux

Two limits remain and are stated above: the connection limit does not cover neighbouring containers or an attacker
with hundreds of addresses, and `docs/PLAN.md` §7.2 and §11 still word the end-to-end encryption as if it existed
(the plan was not edited here). Rows X15–X17, L1–L4, R8 and R9, the four must-fail jobs, the macOS job and 7
checks in `test-config.sh` are the tests the fixes added.

## Not proven until the real server

1. **The server's actual Traefik**: its version and whether `/etc/dokploy/traefik/traefik.yml` was ever edited
   (timeouts, middlewares). The Dokploy CLI's detail calls return HTTP 400, so neither was read. Dokploy shows the
   image under Remote Servers → Setup Server → Validate.
2. **Let's Encrypt** for `relay.martand.systems`: HTTP-01 through port 80, with the resolver as that server has it
   (the default e-mail is `test@localhost.com`). CI used its own CA. An existing HTTPS site on that server with a
   valid certificate would show the resolver works. Until the first certificate is issued Traefik serves its own
   default certificate, and the clients refuse it and retry.
3. **Dokploy's own deploy**: the clone through the GitHub app, its rewrite of `compose.yaml` (it has to keep the
   file's own middleware labels and add the Domains entry's `middlewares=` line: read in Dokploy's source at
   v0.31.1 and v0.31.2, shown by *Preview Compose*), the env file from the Environment tab, the build on the server
   (it downloads chisel from GitHub and pulls Alpine), and Docker Engine 25 or later there for `start_interval`.
4. **A real network path**: NAT, carrier and hotel idle timers, the office's outbound firewall, WSL2's NAT, real
   latency and bandwidth. The 25 s keepalive is there for these; only a hop that cuts after 45 s was tested. Not
   tested at all: a network that only lets HTTP out through a proxy, and one that intercepts TLS.
5. **The real clients**: chisel on the office PC's WSL2 distro as `mu` and on the Mac, the Mac sleeping and
   changing networks, the PC rebooting with the client under systemd, and the lock-out after an unclean restart
   there (the replica froze a container).
6. **Idle for longer than 20 minutes**, and days of uptime.
7. **Life next to the other 12–15 containers**: their deploys, the server's memory, a Traefik update or a reboot of
   the server. One neighbour was tested, and it changed Traefik's configuration through container labels.
   Dokploy's Application-type services change it through files in Traefik's `dynamic` folder; that path was not
   exercised.
8. **The address Traefik sees for a client** on the real server. The connection limit counts per address, so
   `relay.martand.systems` has to point straight at the server; behind a proxy every client would share one limit.
9. **The inner layer** (agent TLS and token, PLAN §7.2) does not exist yet. The test payload was plain HTTP inside
   the tunnel.

## First check on the real server

The Dokploy steps are in `relay/README.md` §2; the owner does them in the UI. Since the review, the Domains entry
also gets **Middlewares: `mu-relay-inflight@docker`**. The values for the Environment tab come from
`relay/gen-credentials.sh`, run by the owner on the Mac (state in `~/.config/mu/relay.env`, mode 600):

```sh
relay/gen-credentials.sh init
relay/gen-credentials.sh add-client compute office-pc 7001
relay/gen-credentials.sh add-client workstation avi-mac 7001
relay/gen-credentials.sh env        # the two lines to paste: RELAY_KEY=… and RELAY_CLIENTS=…
```

After the deploy, `curl -sS https://relay.martand.systems/health` prints `OK` with a valid certificate. Then, with
the fingerprint and passwords from `gen-credentials.sh client office-pc` and `client avi-mac`:

```sh
# office PC, in the mu-compute distro, as mu (no sudo needed): chisel, a stand-in for the agent, the reverse tunnel
mkdir -p ~/s4-check/www && cd ~/s4-check
curl -fsSL -o chisel.gz https://github.com/jpillora/chisel/releases/download/v1.12.0/chisel_1.12.0_linux_amd64.gz

AUTH='avi-mac:<RELAY_PASSWORD>' CHISEL_WS_TIMEOUT=10s ./chisel client --fingerprint '<RELAY_FINGERPRINT>' \

```

The stand-in serves one file from an empty folder: until the agent exists, whatever the PC exposes on that port is
readable by anyone holding the workstation's credentials, and by the server's administrators.

Then three more steps, each read from the two client logs:

1. **Idle.** Leave both clients running for an hour and repeat the `curl`. Each log still has one `Connected` and
   no `Disconnected`.
2. **Relay restart.** In Dokploy press **Stop**, wait until both logs show `Disconnected`, then press **Deploy**.
   Both logs show a new `Connected` (in the replica about 10 s after the relay was up again). Repeat the `curl`
   after that line, not after a fixed time. Pressing Deploy alone is not this test: with nothing changed Docker
   keeps the running container, and no `Disconnected` means "not replaced", not "passed".
3. **Redeploy and revocation.** `relay/gen-credentials.sh rotate-client avi-mac`, paste the new `env` output, Save,
   Deploy. The changed environment replaces the container: the PC's log shows `Disconnected` and a new `Connected`
   (13 s in the replica). The Mac's client still has the old password and is now refused (`Authentication
   failed`); started again with the new one it connects, and the `curl` works.

That checks Let's Encrypt, Dokploy's own deploy and the released chisel binaries on both machines for the first
time, and gives a first sample of a real network path. It does not read the server's Traefik version or
configuration, and it does not cover sleep, roaming, a reboot of the PC or systemd.

## Decision

S4 passes in the replica: chisel behind Dokploy's Traefik on 443 is the relay (PLAN §7.3 Stage A). In the replica
no Traefik setting has to change and no host port is needed. The fallbacks stay in reserve until the first check
on the real server has passed, and are dropped then. Fixed by this spike for P6:

- clients run with `--keepalive 25s`, `--max-retry-interval 15s`, `CHISEL_WS_TIMEOUT=10s` and a pinned fingerprint;
- the relay's health check keeps `start_period` and `start_interval`;
- every client has its own credentials and one access rule, made by `gen-credentials.sh` (later `mu relay add-client`);
- the relay's Domains entry names the connection-limit middleware;
- the Dokploy service gets Watch Paths `relay/**`, so that only relay changes redeploy it;
- `mu` allows about a minute after a network change or a restart of the compute node before it falls back to
  `local`;
- nothing confidential goes through the relay before the agent's own TLS exists.
