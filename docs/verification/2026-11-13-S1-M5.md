# Verification: S1 (reproducible macOS build) and M5 (JATAYU on μ), 2026-11-12/13

## S1: fresh install from GitHub on macOS arm64 (M1, 16 GB)

**Method:** clone `martand-systems/mu` and run `install/install-mac.sh` in a clean environment (`env -i`, `PATH=/usr/bin:/bin:/usr/sbin:/sbin`).
Everything is downloaded from the pinned URLs and checked against SHA-256 / conda MD5.

**Problems found and fixed, in order.** Each was something the hand-built legacy toolchain depended on without writing it down:

| # | Problem | Fix |
|---|---|---|
| 1 | `/usr/bin/git` is Apple's stub and fails until the Xcode licence is accepted | Installer needs no git: CadQuery and text-to-cad are pinned as GitHub source archives; the commit is read from `.git` directly |
| 2 | `PrusaSlicer.app` sits inside `Original Prusa Drivers/` in its DMG | `source_item` path in `apps.toml` |
| 3 | pip rejects local paths containing spaces | Local packages passed as percent-encoded `file://` URLs |
| 4 | The CAM env couldn't import FreeCAD: the legacy venv had an undocumented `freecad.pth` | Installer writes it, then checks `import FreeCAD, ocp_freecad_cam` |
| 5 | OpenFOAM rejects case paths with spaces (`fileName::stripInvalid`), and `~/Library/Application Support` has one | Default install root is `~/Library/Mu` |
| 6 | Annotated release tags weren't detected without git | Peeled `packed-refs` parsing |
| 7 | text-to-cad's registry was shared across μ versions; removing one version broke `cad run` in another | Per-version text-to-cad state; installer fails if registration fails; `mu doctor` checks it |

**Result (v2026.11.0 and v2026.11.1):** `mu doctor` 19/19 (20/20 with the registry check). Benchmarks 6/6: cad-solid,
fea-cantilever, aero-vlm-wing, cfd-cavity, slice-print and cam-plate. Each has its known-answer checks, **plus a regression match
against metrics recorded on the legacy toolchain** (`benchmarks/reference/osx-arm64.json`).

**Benchmark finding:** the legacy setup report's aero smoke test claimed CLα +2.0% vs Helmbold for a rectangular AR 6 wing.
VSPAERO actually gives 4.23 /rad. An independent vortex-lattice solver (`benchmarks/aero-vlm-wing/reference_vlm.py`) converges
to 4.22–4.24 /rad, so VSPAERO is right. Helmbold assumes elliptic loading and overpredicts this wing by ~7%. The old +2% result was
probably a mis-set case: VSPAERO's default `Sref` is 100 in manual mode, which silently scales every coefficient. The benchmark now uses the
independent solution as its reference, and Helmbold only as a ±10% sanity band.

## M5: JATAYU frame analysis re-run on μ v2026.11.0 vs the committed baseline

**Method:** copy of `martand-systems/jatayu` with only `mu` on PATH (legacy toolchain not activated). The full `frame/README.md`
sequence ran (mass, checks, tolerance, FE benchmark and sweep, 7 hub variants, two finer `L_final` meshes, CFD `wind_L4`,
CAM, figures, report), then the text-to-cad build with STEP exports and PrusaSlicer. All steps succeeded. Total time ≈ 55 min, of which CFD was 24 min.

| Output | μ vs committed baseline | Explanation, tested against the legacy toolchain |
|---|---|---|
| `mass.json`, `checks.json`, `tolerance.json` | identical | deterministic |
| `iterations.json` (modes, gimbal frequency, tip stiffness) | ≤ 0.15 % | Gmsh 3D meshing (HXT, 4 threads) isn't deterministic: **two legacy runs give different node counts** (23,663 vs 23,636), and μ runs fall inside the same spread |
| `arm_bench.json` | tip deflection ≤ 0.02 %; error-% fields ≤ 1.2 % relative | same mesh noise; benchmark conclusions unchanged |
| `arm_sweep.json`, `hub_runs.json` | design quantities within mesh noise; large *relative* changes only in near-zero values (displacements ~1e-5 mm) and peak stresses at singular bonded corners | mesh noise on quantities the validation policy already excludes (singular peaks) |
| CFD `forces.json` | drag min/max ≤ 0.2 %, viscous 0.6 %; side force and lift (near zero) and drag std. dev. differ | mesh/convergence noise on small quantities; mean drag reproduces |
| CAD exports (hub plate, leg bracket, hub clamp) | volumes identical | deterministic |
| CAD export `frame_structure` | **μ == legacy exactly (1,053,037.143 mm³)**; committed STEP 1,062,429 mm³ | committed STEP is **stale**: exported from an earlier design iteration |
| Slicing `leg_bracket` | **μ == legacy exactly (48.74 g)**; committed G-code 44.66 g | committed G-code is **stale**: sliced from an older STL or profile |
| CAM `hub_plate_grbl.nc` | identical except the output-timestamp line | deterministic |
| Design report | rebuilt | |

**Conclusion:** μ v2026.11.x reproduces the legacy toolchain. Where the tools are deterministic it matches exactly. Elsewhere it stays within the
legacy toolchain's own run-to-run variation. Two committed JATAYU artefacts don't match the current design inputs (frame
STEP, leg-bracket G-code). That's a JATAYU data issue, reported to the project, and not a toolchain difference.
